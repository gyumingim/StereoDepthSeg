# 폰 재생: VIO 설정별 처리 시간 (2026-10-25, S24, arlat 0.6.17 ov_bridge, 카메라 없음)

녹화 데이터를 실시간 속도로 폰의 브리지에 넣어 설정마다 프레임 처리 시간과 OpenVINS 단계별 시간을 쟀다.
adb shell 만 썼다 (카메라·arlat 화면 안 켬). 전체 표 = `tables.md`, 중간 요약 = `INTERIM.md` (첫 4 run 시점).

## 결론 먼저
1. **33 ms 를 넘는 순간 "절벽"이 있다.** 한 프레임이 33 ms 를 넘으면 다음 프레임이 이미 기다리고 있어 idle spin 이 돌 틈이 없다.
   그러면 병렬 부분이 idle_spin 0 과 비슷해져 느려지고 (tracking 5–7 → 15–20 ms 로 2–3 배, remap 약 2 배), 계속 밀린다.
   증거: 같은 c4s100 을 0.5 배속으로 넣으면 (밀리지 않음) p50 24.4 ms, tracking 5.4 ms / 1 배속은 37 ms, tracking 15 ms.
   idle_spin 0 run 은 밀리지 않는 초기화 전 구간에서도 remap 4.6 배, feed 4 배 느렸다.
   같은 run 안에서도 (같은 클럭) spin 대기가 없던 프레임 (= 밀린 프레임) 은 remap 이 더 길었다: D_c4_1x 3.11 vs 2.11 ms (feed 25.5 vs 15.4),
   R2_c4 3.21 vs 2.34, D_c4n400s100c20_half 4.26 vs 2.16. live 의 마지막 15 s 도 같은 모양 (remap 1.5 → 3.2 ms).
   → 설정의 "자기 비용"이 작아도 합계가 30 ms 근처면 절벽을 넘어 실제 처리 시간은 훨씬 커진다.
   단 원인 방향 (느린 프레임 → spin 없음 인지 그 반대인지) 과 열 상태 영향은 완전히 분리하지 못함 → 그럴듯한 설명이지 증명은 아님 (추정).
2. **1 배속, idle_spin 2, threads 2 결과 (폰이 따뜻한 상태, SKIN 35.3–36 °C 시작):**

   | 설정 | run | 처리 p50 / p95 / 최대 ms | 33 ms 초과 | 실시간 대비 밀림 (최대) | n_slam | ATE cm |
   |---|---|---|---|---|---|---|
   | c4 (점 200, SLAM 50, clone 15) | 3 | 15.2\* / 20.9 / 19.0 · p95 21–35 · 최대 30–56 | 0–8 % | 0.03–0.23 s (회복) | 50 | 0.30 |
   | c4c20 (clone 20) | 1 | 30.0 / 45.1 / 75.9 | 35 % | 2.6 s | 50 | 0.30 |
   | c4n400 (점 400) | 2 | 33.7 / 45.5–48.7 / 62–70 | 52–53 % | 5–8 s | 50 | 0.33 |
   | c4s100 (SLAM 100) | 2 | 36.9–37.5 / 54 / 70–71 | 69–71 % | 13–14 s | 100 | 0.29 |
   | c4n400s70c20 (SLAM 70) | 1 | 41.7 / 61.6 / 95 | 78 % | 22 s | 70 | 0.33 |
   | c4n400s100c20 (사용자 live 설정) | 2 | 47.8–48.8 / 68–71 / 95–105 | 90–95 % | 33–37 s | 100 | 0.32 |

   \* c4 첫 run 만 식은 상태 (SKIN 32.1 °C) 시작 → 15.2 ms. 따뜻한 상태 두 번은 20.9, 19.0 ms.
   참고: idle_spin 0 은 c4 29.4 ms (28 % 초과), c4n400s100c20 45.0 ms. threads 4 는 c4n400 31.9 ms (2 ms 나음, 43 % 초과).
3. **각 옵션의 자기 비용 (단계 시간, 1 배속 따뜻한 run 중앙값 기준, c4 대비):**
   - **max_slam 50 → 100**: slam update 2.8 → 9.2 ms (+6.4), propagation +0.5, re-tri&marg +0.6, msckf −0.7 → **약 +7 ms**.
     max_slam 70 (n400c20 기준): slam update 5.6 ms → 50 대비 약 +3 ms. SLAM 비용은 점 수에 비례 이상으로 커짐.
   - **num_pts 200 → 400**: msckf 1.9 → 5.1 (+3.2), re-tri&marg +1, tracking (밀리지 않을 때, 0.5 배속 짝 비교) +3.6 (5.4 → 9.0) ~ +4.6 (6.8 → 11.4) → **약 +8–9 ms**.
   - **max_clones 15 → 20**: 단계 합 약 +1 ms (추정) — 그런데도 1 배속 run 이 절벽을 넘었다 (c4 자체가 따뜻할 때 p95 33–35 ms 로 경계에 있어서).
   - 밀리지 않을 때 (0.5 배속) 총합: c4s100 24.4 ms, c4n400s100c20 38.1 ms (n_slam 100 에서 이미 33 ms 초과), c4 21.3 ms (클럭이 더 낮던 때).
4. **사용자 live 결과 설명**: live c4n400s100c20 은 초기화 뒤 약 34 s 동안 n_slam ≈ 0 (방 장면) 이라 14–15 ms, 마지막 15 s n_slam 83 일 때 32 ms
   (slam update 9.4, re-tri&marg 7.0, tracking 10.1 ms). 재생의 n_slam 100 단계 비용 (slam update 9.8–10.3 ms) 과 맞는다.
   이 재생 장면 (보드 앞) 은 처음부터 끝까지 n_slam 이 max_slam 에 붙어 있어 live 의 "마지막 15 s" 상태가 계속되는 셈이다.
5. **정확도**: 모든 설정 ATE 0.29–0.33 cm (보드 GT, 카메라 위치 자). 점 400·SLAM 100 이 이 녹화에서는 정확도 이득이 없다.
6. **권장**: S24, threads 2 에서는 **c4 (점 200, max_slam 50, clone 15) 유지**. 따뜻한 상태에서 c4 도 p95 가 33 ms 근처라 여유가 없다.
   max_slam 을 올리려면 70 이하 (c4 + 약 3 ms, 추정) 이고 그것도 절벽 위험이 있다. 점 400 과 SLAM 100 은 빼는 것이 맞다.
   여유를 만들려면 먼저 절벽을 없애야 한다 (처리 중에도 풀 스레드를 깨워 두기, 늦은 프레임 버리기, 큰 코어 고정 `--cpus 7,8,9` 시험 — 아래 할 일).

## 방법
- **입력**: `hs_20261021_213341` (240 fps HS 녹화, 1920x1080, 초점 2.22 dpt, 보드 GT 있음) 의 trim 시작부터 80 s.
  30 fps 로 시간 기준 프레임 선택 (vio_bench_hs.fed_selection), 2327 프레임 (녹화 자체 공백 때문에 평균 29.1 fps, 최대 간격 100 ms).
  cam5.mp4 디코드 → 회색 1920x1080 **원본 (왜곡 안 폄)** → 브리지가 앱과 같은 `--remap remap_1920x1080.bin` (960x540) 으로 폄 → remap 비용 포함.
  IMU = raw 16/35, 가속도는 자이로 시각에 보간, 자이로 rebias 없음 (앱과 같음). 프레임 시각 = t_mid − align dt (−3.37 ms, IMU 시계),
  그래서 kalibr `timeshift_cam_imu` 만 0 으로 바꿈 (폰 yaml 은 0.002172 = 평균 가정값). 순서: 프레임 시각 + 5 ms 까지의 IMU 뒤에 프레임.
  만든 스크립트 `scripts/make_raw_stream.py`, 프레임 시각 `stream/raw80_frames.json`.
- **std60 녹화를 안 쓴 이유**: std60 (현재 live 렌즈 설정) 녹화는 모두 ≤ 35 s. 12 s 는 너무 짧다는 지시대로 HS 긴 녹화를 썼다.
  폰 remap 은 0.5 dpt 초점용이라 2.22 dpt 녹화와 초점 거리 약 1.4 % 차이 (가정) — 모든 설정에 같게 들어가므로 비교에는 영향 작음.
- **폰으로 옮기기**: adb (tailscale wifi) 가 0.4 MB/s 라 원본 4.8 GB 를 못 보냄 → H.264 (libx264 crf 20, yuv420p, Y = 회색) 153 MB + 영상 없는
  레코드 파일 (`side.bin`) 을 보내고 폰에서 `unpack` (NDK + OpenCV MediaNDK 디코드) 으로 같은 형식의 4.8 GB 스트림을 다시 만듦.
  디코더의 YUV→BGR→회색 변환이 명암을 1/0.889 배 늘려서 경험적 LUT (`lut.h`, `cmpf.py`) 로 되돌림.
  폰 프레임 vs 원본: 평균 절대 차 2.2 회색값 (PC Y 디코드 vs 원본 1.6–1.7). **모든 폰 run 이 같은 입력**.
- **설정**: 폰 앱 폴더의 yaml 그대로 (`config/phone_ov_main/*` 와 같음 확인), 경로만 바꿈 → `cfg/`.
  `c4n400s70c20` = c4n400s100c20 의 max_slam 100 → 70, `c4s70` = c4 의 50 → 70 (둘 다 로컬만, 커밋한 config 아님).
- **브리지**: 0.6.17 바이너리 (`/data/local/tmp/predict/ov_bridge_0617`, predict 검사와 같은 것), 앱과 같은 인자:
  `--stdio --max-speed 8 --lost-frames 1000000 --startup-lost-frames 1000000 --remap remap_1920x1080.bin --timing-log tl.csv --threads N --idle-spin S`
  (predict 0). OpenVINS `record_timing_information: true` → `ov_timing.txt`.
- **공급기**: `feeder2` (NDK, 레코드 시각대로 잠자며 보냄, 디스크에서 64 MB 미리 읽기), `feeder3` = 속도 배율 추가 (0.5 = 반 속도).
  브리지가 느리면 파이프가 차서 공급기가 막힘 → 프레임을 버리지 않고 밀린다 (앱이 늦은 프레임을 어떻게 다루는지는 확인 안 함).
- **온도**: 매 run 전 SKIN (`dumpsys thermalservice` 의 "Current temperatures from HAL" 부분) < 36 °C 까지 10 s 마다 확인 (사용자 지시로 34 → 36 완화),
  run 중 SKIN ≥ 38 이면 중단. 시작/끝/최대 SKIN 과 AP 를 `phone/<run>/run.txt` 에 기록. 순서는 가벼운/무거운 설정을 섞음.
- **채점**: 처리 시간 = remap_ms + feed_ms (브리지 타이밍 로그, 추적 단계 프레임). 단계 = ov_timing.txt. 밀림 = (브리지 수신 시각 − 카메라 시각) − 최소값 + 처리.
  ATE = T_world_cam0 위치 vs `imu_gt_spl_cal1022` (가장 가까운 GT < 2 ms, SE3 정렬 RMSE). `scripts/analyze.py`, `final.py`.
- PC 기준 (원본 스트림, build_par 브리지, threads 2, 빠르게): c4 11.5 ms, c4n400s100c20 27.5 ms (`pc/`). 폰 초기화 시각 11.47 s 가 PC 와 같음.

## 섞인 변수 · 한계 (중요)
- **폰 열 상태가 run 마다 다르다**: SKIN 은 선풍기로 36 °C 근처에 머물지만 CPU 클럭 상한은 계속 움직였다
  (큰 코어 최대 3.2 GHz (cpuinfo_max_freq) 중 run 중 중앙값 2.0–2.2 GHz (10:59–11:06) → 1.6–1.8 GHz (11:06 이후)). 초기화 전 구간 (모든 설정이 같은 일) 의
  remap/feed p50 을 속도 지표로 `tables.md` 에 넣었다: 1.3–1.8 / 3.3–4.3 ms (R1_c4n400 · R1_c4s100 은 1.7–1.8 로 느린 편),
  H_c4n400 · H_c4n400s70c20 은 1.9 / 4.9 ms (약 30 % 느린 상태), threads 4 run 은 0.98 / 3.1 (4 스레드 효과 + 빠른 클럭 상태가 섞였을 수 있음).
  이 지표는 초기화 전 짧은 구간이라 run 중 클럭 변화는 못 잡는다. 0.5 배속 run 은 모두 10:59 이후 (순서 섞임 아님).
  밀리지 않는 run 에서도 처리 시간이 run 앞→뒤로 늘었다 (H_c4_half 처음 200 프레임 17.0 → 마지막 200 프레임 26.1 ms, R1_c4 15.2 → 18.4) → 장면 또는 열 영향도 있음.
  idle_spin 0 의 c4n400s100c20 (45.0) 이 spin 2 (47.8–48.8) 보다 조금 빨랐다 — 둘 다 밀린 상태라 spin 이 못 돌고, 클럭 상태 차이 또는 spin 이 코어를 쓰는 비용일 수 있음 (미확인).
  → H 의 두 run 은 비교에서 낮은 신뢰. H_c4n400s70c20 은 0.5 배속인데도 밀렸다 (최대 505 ms 프레임).
- **사용자가 폰을 썼다**: 11:19:32 에 화면이 켜지고 다른 앱이 앞에 옴 (그 뒤 SKIN 38.9 °C 로 H_c4c20 중단, adb 연결 잠시 끊김).
  11:16:26 화면이 시간 초과로 꺼진 기록만 있고 그 전 사용 여부는 로그가 지워져 모름 → 11:06 이후 H run 은 사용 영향 가능성 있음.
  남은 run (`scripts/list7.txt`: c4 3 회째, c4s70, `--cpus 7,8,9` 고정 시험, c4s70·c4c20 0.5 배속) 은 화면이 꺼질 때까지 기다리다 **돌리지 못함**.
- adb shell 은 root cgroup, 카메라·ISP·앱 스레드 부하 없음 → 절대 ms 는 live 와 다르다. 대신 공급기가 2 MB 프레임을 파이프로 복사 (CPU 약 0.6 코어).
  live c4 (idle_spin 0 run) 는 tracking 8 ms 로 재생 (idle_spin 2) 의 5–7 ms 보다 컸다.
- 이 장면은 특징이 많아 n_slam 이 늘 최대 → n_slam 구간별 비용은 사실상 max_slam 값 (50/70/100) 세 점과 초기화 직후 몇 프레임뿐.
- 1 배속 run 의 단계 시간에는 절벽 영향이 섞여 있다 (병렬 단계: remap, tracking). msckf · slam update · re-tri&marg 는 절벽 영향이 작았다 (0.5 배속과 비슷).
- H.264 재압축 (평균 차 2.2 회색값), 초점 1.4 % 차이, 첫 run 만 식은 상태.
