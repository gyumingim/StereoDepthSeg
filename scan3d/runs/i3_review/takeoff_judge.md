## 1. 최종 판정 (결론 먼저)
- **A: 재실행은 비트 동일 — 맞음.** 그래서 같은 설정을 다시 돌리는 잡음은 0 이다. 하지만 이것은 "실제 잡음 크기"가 아니다. 의미 있는 잡음은 클립 시작 위치를 조금 바꿀 때의 차이(시작 위치 민감도)다. 같음 띠 0.05 cm 는 등록 규칙대로 유지하되, 다음 시험에서는 시작 위치 민감도를 따로 잰다.
- **B: "i3 이득 확인 안 됨" — 사전 등록 규칙대로 유지.** 숫자는 검증자가 독립 재계산으로 모두 재현했다.
  - 다만 이유를 바르게 써야 한다. "i3 가 나쁘다"가 아니라 **"무너짐이 난 녹화가 214550 하나뿐이라 기준 (ii)를 처음부터 채울 수 없었고, (iii)의 모은 중앙값은 i3 가 막은 칸의 값까지 섞여 올라갔다"**.
  - 같은 칸끼리 차이(i3 − base) 12 개의 중앙값은 0 이다 (직접 확인: −88.6, −56.0, −42.1, −0.15, 0×4, +0.05, +0.93, +1.17, +1.47 cm).
  - 그래도 **작은 악화 신호는 진짜로 있을 수 있다.** i3 가 작동한 214550 밖 칸 5 개 중 3 개가 0.9–1.5 cm 나빠졌다 (213341 d1/d5, 215348 d5). 시작 위치 민감도 안인지 밖인지는 모른다 (불확실).
- **B′: "확인 안 됨" — 규칙대로 유지.** 이미 추적 중인 정지에서는 base 가 출발에서 무너지지 않았다 (213955_o2 는 충격으로 둘 다 무너짐). 단, 214550 에서는 무너짐 문턱(10 cm) 아래로 i3 가 4–5 배 좋았다 (base 2.8–3.7 cm vs i3 0.59–0.81 cm). 이것은 **사후 관찰**이라 점수가 없다.
- **C: 기작 미상 — 유지.** "핵심 차이는 ZUPT 통과율" 은 빼야 한다. i3 의 높은 통과율은 i3 가 붙잡은 영상(시차 0) 때문에 생긴 것, 곧 i3 가 하는 일 자체이고 원인 설명이 아니다.
- **앱 설정: i3 는 계속 넣지 않는다 (이전 판정 그대로).** 214550 같은 "시차 잡음 정지"에서는 i3 가 무너짐을 크게 줄였지만 녹화 1 개뿐이다 (추정).

## 4. 과정 이탈의 무게
**전체 무게: 작다. 어떤 판정도 바꾸지 않는다.** 이유: 결론이 모두 "확인 안 됨" (보수적인 쪽) 이라 이탈이 결과를 부풀린 방향이 아니다.
- B′ 를 실행 중 추가: 작음. B′ 값을 계산하기 전에 커밋 (0ae82ca 00:50:37), B 규칙은 안 바뀜. 다만 실행 가능성을 먼저 확인하지 않아 낭비가 컸다.
- 분석 코드 완성 전 B 결과 1 개를 봄: 작음. base 한 실행, 기준은 이미 커밋. 그러나 036584f 커밋 메시지가 사실과 다르므로 결과 문서에 정정 한 줄.
- B′a 가 이미 본 실행: 작음 (판정용). 그러나 B′a 의 "4–5 배 이득" 같은 연속 값은 **사후 분석**으로만 말한다.
- UNC 경로 sed -i: 판정 영향 없음. docs 6 파일 모드만 바뀜 (원인 불확실). `git diff` 로 내용 0 확인 후 `chmod 644` 로 되돌리고 커밋하지 않는다. 앞으로 UNC 경로 파일은 WSL 안에서 고치거나 Edit 도구로 고친다.
