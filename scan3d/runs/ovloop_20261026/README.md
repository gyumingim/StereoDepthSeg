# ovloop 2026-10-26 — 루프 닫기 v1 + 장소 재인식 비교 (BoW vs BoQ vs SALAD)

브랜치 `ovloop-20261026`. 계획 = `PLAN.md`, VPR 스크립트 = `README_vpr.md`. 모든 기능은 `--loop 1` 일 때만 (기본 0 = 기존과 동일).

## 결론 (먼저)
- 이 데이터(HS 42칸, std60 165506, 손 루프 2개)에서는 **BoQ·SALAD 가 BoW 보다 나은 점이 측정되지 않았다.** 루프 수·recall·ATE 거의 같고,
  틀린 루프는 BoW 0, BoQ 2, SALAD 1 (모두 각도 3.2° 로 3° 문턱을 살짝 넘은 경계 사례, 위치 오차 3.6–4.2 cm).
- 제한 요인은 **후보 찾기가 아니라 기하 확인** (특징 매칭 수 부족). 흰 벽 손 루프에서 세 방식 모두 "끝 → 시작" 후보를 냈지만 (BoW 6/5, BoQ 4/5, SALAD 6/9 개)
  전부 매칭 부족(`matches`/`matchesB`)으로 거절, 인라이어 0. 시작 키프레임 3D 점 0 개.
- 폰 권장: **BoW v1 유지** (질의 0.2 ms, 키프레임당 루프 스레드 PC 29 ms / 폰 35 ms p50). VPR 은 넓은 공간·조명 변화가 생길 때 다시 (BoQ 우선: MIT).
- `weight_mode=1` (시그마 가중 그래프, B30w): HS42 좋아짐 19 / 나빠짐 10 (B30 15/16) 이지만 중앙값 차 0, std60 은 나빠짐 (1.58 vs 1.48 cm) → **기본값 0 유지, 채택 안 함**.

## 폰에 VPR 을 올린다면 (전부 추정)
- BoQ (MIT) 우선; SALAD 는 GPL-3 이라 앱 배포 시 앱 전체가 GPL.
- 경로: PyTorch → ONNX (고정 322x322) → LiteRT (ai-edge-torch 또는 onnx2tf) fp16 GPU delegate. NPU int8 은 ViT 연산 일부가 CPU 로 떨어질 수 있음.
- ViT-B/14 약 90 M 파라미터, fp16 ~175 MB, 폰 GPU ~100–300 ms/KF (추정) → 키프레임 1–2 Hz 면 가능하지만 지금 데이터에선 얻는 것이 없음.
- 다른 길: 키프레임을 PC 로 보내 PC 에서 계산 (폰 부하 0).
