> - 결론 3 의 "지렛대가 일정하고 OpenVINS 와 독립 일치" 는 **과장**. x·y 는 맞지만 **z 는 녹화(세션)마다 −0.07…−2.23 cm 로 다르고 불확실** (OpenVINS 도 z −0.2…−2.1).
> - 결론 4 의 "노트북 칸 32.03 mm 가 1.5–2 % 작다 (≈ 32.6 mm)" 는 **철회**. 사용자가 자·카드로 노트북 0.1570 mm/px 를 확인함. 보드별 s 는 방법(지렛대 맞춤/고정, q2)에 따라 0.6–1.7 % 달라지고 모니터 보드도 1–2 % 편향이 남는다 → 보드별 s 차이는 칸 크기 근거가 아님. "다음에 고칠 것 2" (노트북 칸 다시 재기) 도 취소.

## 결론 (먼저)
1. **바닥은 축척 오차가 아니다.** 잘 된 VIO 15 개 실행에서 SE3-ATE 중앙 **0.58 cm**, Sim3-ATE 중앙 **0.55 cm**. 축척이 설명하는 몫은 √(SE3²−Sim3²) 중앙 **0.18 cm** (0.11–0.58).
2. **바닥의 대부분은 느린(0.2 Hz 미만) 표류, 주로 중력 방향(위아래)이다.** Sim3 오차를 주파수로 나누면 0.2 Hz 미만 **0.51 cm**, 0.2–2 Hz 0.24 cm, 2 Hz 초과 0.08 cm. 10 s 구간마다 Sim3 를 다시 맞추면 **0.21–0.25 cm** 만 남는다 (노트북 녹화).
   GT 쪽 잡음은 작다: GT 고주파 떨림 0.06–0.12 cm, GT 두 방식(rs vs spl) 차이 0.04–0.11 cm, IMU 1 s 창 잔차(지렛대 포함) 0.04–0.08 cm.
   오차는 "자세의 함수"보다 "시간의 함수"에 가깝다 (자세로 맞춘 모델이 다른 10 s 묶음에서 설명력 R² ≤ 0.18, 대부분 음수). → **바닥은 주로 VIO 표류 (추정).** 느리고 자세에 따라 반복되는 GT 오차는 이 방법으로 다 못 잡으므로 최대 약 0.2 cm 까지는 GT 일 수 있다 (추정).
3. **GT 축척 점검의 s ≠ 1 과 ±4 % 흔들림은 대부분 점검 방법 탓이다: IMU–카메라 지렛대(lever arm)를 빼먹었다.** `scale_ls.py` 는 IMU 위치 = 카메라 위치로 두는데, 실제로는 카메라 좌표에서 약 **(0.5, 4.6, −1.1) cm** 떨어져 있다.
   지렛대를 같이 맞추면 녹화 17 개의 s 표준편차가 **0.044 → 0.010** 으로 줄고, 창 잔차도 0.19 → 0.12 cm (가속도 일정항까지 빼면 0.10 → 0.056 cm).
   맞춘 지렛대는 녹화 17 개에서 같고 (y 4.6 ± 0.2 cm), **OpenVINS 가 온라인으로 따로 추정한 p_IinC0 (0.4–0.6, 4.5–4.7, −0.8…−1.2 cm) 와 같다** — 독립된 두 방법이 일치.
4. 지렛대를 고친 뒤 남는 축척: **모니터 보드 1.008 ± 0.009 (10-19 녹화 11 개)**, **노트북 보드 1.025 ± 0.007 (10-21 녹화 4 개)**. 노트북 보드만 약 **+1.7 %** 더 크다 → 노트북 칸 크기 32.03 mm 가 약 1.5–2 % 작게 잡혔을 가능성 (추정; 실제 ≈ 32.6 mm, 0.160 mm/px). VIO 도 노트북 GT 보다 1.5 % 크게 본다 (VIO/GT 중앙 1.016) — 같은 방향.
5. 가속도계 이득은 원인이 아니다: 정지 구간 |a| (원본 type 35) = **9.7855 m/s²** (+x 면, 정지 36 개) vs 서울 g 9.7995 → **−0.14 %**. 축척 점검의 맞춘 중력 크기도 9.78–9.80. 렌즈 fx, 시간차, 롤링셔터도 1 % 미만 (표 A).

**다음에 고칠 것 (순서)**
1. `scale_ls.py` 에 지렛대 3 개 미지수 추가 (또는 고정값 (0.5, 4.6, −1.1) cm 사용). 지금의 overnight "scale check" 숫자는 ±4 % 가 방법 잡음이다. (이 작업에서는 고치지 않음; `imu_learn/ate_floor.py scale/scale2` 에 구현돼 있음.)
2. 노트북 보드 칸 크기를 모니터처럼 30 cm 자 모드로 재기 (`docs/charuco_monitor.html` 노트북 모드). 다르면 `rescale_gt.py` 로 GT 축척만 고침. 효과는 ATE 로 0.1 cm 이하 (아래 B).
3. VIO 바닥을 낮추려면 VIO 쪽: 느린 위아래 표류 → 가속도 편향·중력 방향. **6 면 가속도 보정**(지금 정지 자료는 +x 면 뿐이라 축별 이득·편향을 못 나눔) 과 가속도 편향 잡음 설정을 다음 후보로 (추정).
4. VIO 의 지렛대 초기값: `kalibr_imucam_chain.yaml` 의 T_imu_cam 이동이 0 이지만, OpenVINS 가 1 s 안에 4.5 cm 로 수렴하므로 효과는 작을 것 (추정). 초기값을 (0.5, 4.6, −1.1) cm 로 주는 것은 싼 시험.

## 방법·입력 (재현)
- 스크립트: `imu_learn/ate_floor.py` (`still` | `scale` | `scale2` | `vio` | `regress`), 결과 `runs/ate_floor/*.json` (made 시각 포함). 기존 코드·녹화 수정 없음.
- 축척 식은 `scale_ls.windows_eq` 와 같음 (1 s 창, 5 프레임 평균, align.json 의 dt·R_ci, 원본 IMU type 35). `scale` 의 iso s 는 overnight 숫자를 그대로 재현 (213341 1.0407, 111836 1.0263 …).
- 지렛대 모형: p_IMU = p_cam + R_bc r (r 은 카메라 좌표), 선형이라 같은 LS 에 3 열 추가. q2 = 창마다 [1, τ, τ²] 를 빼서 중력·가속도 편향을 창별로 흡수.
- ATE: 벤치 `evaluate()` 와 같은 짝맞춤 (±2 ms, |p|<1.2 m, dt = align_dt_ms), 우리 SE3/Sim3 숫자가 벤치 json 의 ate_cm / ate_sim3_cm 과 0.01 cm 안에서 같음.
- 정지 점검: 1 s 창, 자이로(바이어스 뺀) rms < 0.03 rad/s, 가속도 축별 sd < 0.03. hs_2026102* 와 static_imu_20261020_095113. 서울 g = 9.7995 (Somigliana, 37.5°N, 추정 ±0.0005). 정지 자세가 +x 면(가로 들기) 36 개, −z 2 개뿐이라 축별 이득·편향 분리 맞춤은 퇴화 → 쓰지 않음.
- 반복: 축척 부트스트랩 100–200 회, VIO 실행은 녹화당 시작 3 개 × (base, i3). 섞인 변수: 노트북/모니터 사이에 보드·거리·렌즈 파일·날짜가 같이 바뀜.
- 한계: 지렛대가 빠진 것은 확실하지만 남은 +0.8 % (모니터) 의 원인은 미확인 (가속도 y·z 이득, GT 평활 감쇠 후보, 추정). 노트북 +1.7 % 가 칸 크기인지는 자로 재야 확정.
